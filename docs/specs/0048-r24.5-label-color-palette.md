# 0048 — R24.5 Label color palette (`--palette <name>`)

**Run:** 2026-05-09-r245-label-color-palette
**Tier:** Yellow
**Status:** spec → plan → implement
**Source requirement:** `docs/roadmap.md:446-496`
**Depends on:** R23 (spec 0035, merged), R24 (spec 0036, merged)

---

## Problem

Freelo's label color is a free-form `#RRGGBB` string on the wire, but in practice the UI only renders nine canonical hues. Anything outside the palette is silently snapped on the server. The CLI today exposes `--hex <#RRGGBB>` on three commands (`labels rename`, `labels attach`, `task-labels create`); a user has to memorize hex codes for the supported colors with zero discoverability — the help output does not show them.

This is unfriendly to humans and especially poor for agents, which would benefit from a stable, named enum.

## Proposal

Add a new mutually-exclusive flag pair to the same three commands:

```
freelo labels rename       <id> [--name <str>] [--palette <name> | --hex <#RRGGBB>] [--is-private | --is-public] [--dry-run]
freelo labels attach       --project <id> --name <str>... [--palette <name> | --hex <#RRGGBB>] [--private | --public] [--dry-run]
freelo task-labels create  --name <str>... [--palette <name> | --hex <#RRGGBB>] [--dry-run]
```

`--palette <name>` accepts one of nine names (case-insensitive). The CLI resolves the name to its canonical hex and ships that on the wire — both flags terminate in the same `color: "#RRGGBB"` body field. `--hex` keeps its existing behavior (free-form six-digit hex).

The command's `--help` text gains a long-description block listing the nine palette entries, so `--help` is the single source of truth for what colors the server will actually render.

### Palette (locked at build time)

| Name   | Hex       |
| ------ | --------- |
| gray   | `#77787A` |
| aqua   | `#15ACC0` |
| blue   | `#367FEE` |
| green  | `#10AA40` |
| pink   | `#CA3E99` |
| purple | `#9235E4` |
| red    | `#E9483A` |
| orange | `#F2830B` |
| yellow | `#E3B51E` |

### Behavior

- **Mutex.** `--palette` and `--hex` together → `ValidationError` (exit 2). `hintNext` lists the nine names.
- **Case-insensitive lookup.** `--palette RED`, `--palette Red`, `--palette red` all resolve to `#E9483A`.
- **Unknown name.** → `ValidationError` (exit 2). `hintNext` enumerates the nine names.
- **`--hex` validation unchanged.** Still `^#[0-9a-fA-F]{6}$`. Non-palette hex values still pass through; the server decides what to render.
- **Dry-run.** `would.body.color` shows the resolved hex regardless of which flag was used. No envelope shape change.
- **Help.** Each affected command's Commander long-description block contains the palette table.

## API surface

None. Wire body is unchanged: `color: "#RRGGBB"`. No new endpoint, no envelope schema change, no `/v2` bump.

## Data model

### New file: `src/lib/label-color.ts`

```ts
export const PALETTE: Readonly<Record<string, `#${string}`>> = Object.freeze({
  gray:   '#77787A',
  aqua:   '#15ACC0',
  blue:   '#367FEE',
  green:  '#10AA40',
  pink:   '#CA3E99',
  purple: '#9235E4',
  red:    '#E9483A',
  orange: '#F2830B',
  yellow: '#E3B51E',
});

export type PaletteName = keyof typeof PALETTE;

export interface ResolveColorFlagsInput {
  readonly palette?: string;
  readonly hex?: string;
}

/**
 * Resolves `--palette` / `--hex` to a single wire `color` value or undefined.
 * Throws ValidationError on:
 *  - mutex violation (both flags set)
 *  - unknown palette name (case-insensitive miss)
 * Does NOT validate --hex shape — that stays in the per-command parseHexColorFlag.
 */
export function resolveColorFlags(input: ResolveColorFlagsInput): string | undefined;

/**
 * Returns a multiline string formatted for Commander long-description. Lists
 * the nine palette entries with their hex values, aligned. Used in command
 * registration so `freelo labels rename --help` shows the table inline.
 */
export function paletteHelpBlock(): string;
```

## Edge cases

- `--palette ` (empty) — same as unknown name → ValidationError.
- `--palette red --hex "#ff0000"` — mutex violation, even when both would resolve to the same hex.
- `--palette red --palette blue` — Commander overwrite: the second wins. We don't add custom semantics here; only the final value is checked. (This is consistent with all other repeated single-value flags.)
- Dry-run with `--palette red` — `would.body.color === '#E9483A'`. The render pipeline does not reveal which flag the user passed; only the resolved hex.
- Help block formatting — must be deterministic (alphabetical order does NOT match the requirement table; we keep the requirement order: gray, aqua, blue, green, pink, purple, red, orange, yellow). Frozen palette object preserves insertion order.

## Non-goals

- **No** narrowing of `--hex` to palette-only values. Free-form hex stays accepted.
- **No** envelope schema bump (`freelo.labels.rename/v1` etc. unchanged).
- **No** API change.
- **No** translation of palette names. We're shipping English names; localization is out of scope.
- **No** auto-suggestion ("did you mean 'red'?") on misspellings — `hintNext` lists the nine names, that's enough for v1.
