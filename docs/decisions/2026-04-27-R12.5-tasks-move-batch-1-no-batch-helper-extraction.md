# Decision 1 — Do not extract a new helper into `src/lib/batch.ts`

**Run:** 2026-04-27-R12.5-tasks-move-batch
**Phase:** 2 (spec) — architect
**Agent:** orchestrator (architect role)

**Question:** The roadmap text for R12.5 says "Generalize `src/lib/batch.ts` for
per-row destination params". Should the spec ship a new helper (e.g. a "two-id batch
loop" abstraction)?

**Decision:** No new helper. Reuse the existing primitives — `iterateLines`,
`parseNdjsonLine`, `ExitCodeAccumulator` — which are already schema-generic. The
"first two-id write" is realized at the **command-orchestration layer** in
`src/commands/tasks/move.ts`, not at the library layer.

**Alternatives considered:**

- **Extract `runBatchLoop(stdin, schema, processOne)`** — would consolidate
  R09/R11/R12.5 batch loops. Rejected: each command has subtly different
  per-line success-envelope shapes, lazy-client semantics differ slightly, and
  extracting now would require backporting R09 and R11 to the new helper. That's
  a 3-command refactor unto itself; calibration §4 warns about untested branches
  in cross-cutting helpers. Defer until a 4th batch command lands.

- **Add a `parseTwoIdLine(schema, ...)` variant** — adds zero value over the
  existing schema-generic `parseNdjsonLine`. Rejected.

**Rationale:** `parseNdjsonLine` accepts any `ZodTypeAny`. The R12.5 per-line
schema (`{id, to_tasklist, to_project?}`) plugs in directly. The "generalization"
the roadmap asked for is satisfied by the fact that `src/lib/batch.ts` is **already
general** — it just hasn't been exercised with a richer schema yet. Touching shared
code without need violates "don't refactor in a feature PR" and adds review burden
on a Yellow slice.
