# Decision 2 — 60 s clock-skew clamp on `--at` futures

**Run:** 2026-04-28-2050-r19.5-time-start-backdate
**Phase:** spec
**Agent:** orchestrator (architect role)

**Question:** What's N in "refuse `--at` more than N seconds in the future"?

**Decision:** 60 seconds.

**Alternatives considered:**
- 0 seconds (strict) — harmless clock skew between machines is real.
- 5 minutes — too lenient; a 5-min-future timer makes no sense for a "just started" session.
- No clamp (let server decide) — parent prompt explicitly recommended a clamp; "future timer that just started" is a UX bug worth catching client-side before the server sees it.

**Rationale:** 60 s is the smallest tolerance that comfortably accommodates NTP drift and integration replays without permitting nonsensical futures. Server-side will independently reject anything it deems invalid.
