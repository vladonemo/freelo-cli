# Decision 2 — `--stdin` only; no `--pairs` sugar in v1

**Run:** 2026-04-27-R12.5-tasks-move-batch
**Phase:** 2 (spec) — architect
**Agent:** orchestrator (architect role)

**Question:** The roadmap text suggested `--pairs <id>:<tasklist_id>,<id>:<tasklist_id>`
as optional sugar. Ship it alongside `--stdin`?

**Decision:** `--stdin`-only in v1. No `--pairs` flag.

**Alternatives considered:**

- **Ship both** — adds two parser code paths and an interaction matrix
  (`--pairs` + `--dry-run`? `--pairs` + `--to-project`? `--pairs` with rows that
  include `:project_id`? what about quoting in `bash`?). Rejected: doubles the
  surface area for a Yellow slice and creates an ambiguity-of-source rule
  (`--pairs` AND `--stdin` → which wins?).
- **Ship `--pairs` instead of `--stdin`** — rejected: NDJSON is the contract for
  agent-driven CLIs (envelope-out, NDJSON-in symmetry). Shells already have
  `xargs`/`jq` for ergonomic single-line composition.

**Rationale:** Run-config default was "stdin-only unless architect finds strong
precedent". No precedent in R09 (`tasks create --stdin`) or R11
(`tasks finish/reopen --stdin`); neither ships pair-style sugar. The cost-to-value
of a second input format is negative for a slice that already has multiple new
behaviors (per-row destinations, per-row `to_project` assertion, mutex rules).
Defer to R12.6 if real users ask.
