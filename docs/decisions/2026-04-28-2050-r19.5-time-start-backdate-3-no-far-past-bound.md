# Decision 3 — No client-side lower bound on `--at`

**Run:** 2026-04-28-2050-r19.5-time-start-backdate
**Phase:** spec
**Agent:** orchestrator (architect role)

**Question:** Should the CLI reject `--at` more than e.g. 30 days in the past?

**Decision:** No client-side lower bound. Mirror server behavior.

**Alternatives considered:**
- 30-day soft cap with `ValidationError` and a hint — invents stricter rules than the server.
- 30-day soft warning that still sends the request — we don't have a "warn" channel and adding one for one flag is yak-shaving.

**Rationale:** Roadmap text is explicit: "Mirror whatever Freelo's server-side validation does, don't invent stricter rules." The server's response handling (`FreeloApiError` with `httpStatus: 400/422`) is already in place from R19's HTTP error tests.
