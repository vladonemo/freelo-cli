# Decision 4 — Per-status `hintNext` rewriting on 404 / 403 lives in the command layer

**Run:** 2026-04-26-0914-r04-projects-show
**Phase:** spec
**Agent:** architect

**Question:** Where should the user-facing error hint for "project not found" (404) or "no permission" (403) be generated — in the R01 HTTP client, or in the command's catch block?

**Decision:** Catch `FreeloApiError` in `src/commands/projects/show.ts`. When `httpStatus === 404`, re-throw with `hintNext: "Project ${id} not found, or your account does not have access."`. When `httpStatus === 403`, re-throw with `hintNext: "Account does not have permission to view project ${id}."`. All other statuses pass through unchanged.

**Alternatives considered:**
- Add per-endpoint hint logic to `src/api/client.ts`. Rejected: pollutes the generic HTTP layer with domain knowledge; doesn't scale as more commands need different hints.
- Generic 404 hint without the project id. Rejected: less actionable for agents and humans alike.

**Rationale:** R01's HTTP client deliberately stays endpoint-agnostic (`FreeloApiError.fromResponse` produces a generic mapping). Per-command hint rewrites belong in the command, where the user's input (the project id) is in scope. The pattern is small (a switch on `httpStatus`) and isolates Freelo-API quirks per command.
