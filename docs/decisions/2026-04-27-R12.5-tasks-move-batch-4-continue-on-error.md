# Decision 4 — Continue-on-error in batch (max-of exit codes)

**Run:** 2026-04-27-R12.5-tasks-move-batch
**Phase:** 2 (spec) — architect
**Agent:** orchestrator (architect role)

**Question:** When a single batch line fails (parse, validation, HTTP, network),
should the run abort, or continue processing remaining lines?

**Decision:** Continue-on-error. Each per-line failure emits a `freelo.error/v1`
envelope on stdout; the loop proceeds; the final exit code is the **max** of all
per-line exit codes (`ExitCodeAccumulator` model — POSIX "highest severity wins").

**Alternatives considered:**

- **Fail-fast** (abort on first error) — rejected: inconsistent with R09 and R11,
  which both ship continue-on-error. Agents driving large batches would have to
  re-submit the whole stream after every failure, which is wasteful.
- **Configurable via `--abort-on-error` flag** — deferred: nobody has asked for it.
  Adding a flag for a hypothetical use case is gold-plating.

**Rationale:** Run-config default said "continue-on-error (matches R09 `--stdin`
precedent)". R09 spec 0019 §3.5 and R11 spec 0021 §3.5 both lock continue-on-error
as the default. Consistent semantics across the write surface lets agents share a
single error-handling code path.
