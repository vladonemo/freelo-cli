# Decision 7 — Proceed despite a pre-existing test isolation flake on `test/config/resolve.test.ts`

**Run:** 2026-04-28-2050-r19.5-time-start-backdate
**Phase:** test
**Agent:** orchestrator

**Question:** `pnpm test` on this dev machine reports 1 failing test:
`test/config/resolve.test.ts > buildSourceMap — source attribution > all sources are default when nothing is set`. Should the run pause?

**Decision:** No. Proceed. The failure is **not** caused by R19.5 changes.

**Evidence:**
1. Reproduces on `main` @ `f508dfc` with no R19.5 changes applied (verified by stash + checkout main + run).
2. Root cause: `buildSourceMap` calls `safeReadStore()` which reads the dev user's real `conf` store at `%APPDATA%\freelo-cli\config.json`. The user has `currentProfile` set there, so `profileSource` resolves to `'conf'` instead of the test's expected `'default'`. The test does not isolate the user's `conf` store.
3. Pre-existing across recent commits — commit `f508dfc` itself is the parent run that just shipped a roadmap doc and merged in CI, where this test passes (CI runs on a clean Linux/macOS env without a populated user `conf`).

**Alternatives considered:**
- Pause and ask a human to fix the pre-existing flake — rejected; it's out of scope for R19.5 and would block a Yellow-tier flag-only addition on an unrelated tooling bug.
- Fix the test in this PR by mocking `conf` — rejected; (a) scope creep; (b) the parent prompt's hard constraints don't include "fix unrelated flakes"; (c) other config tests in the same suite already pass with the same code path because they pass explicit `flags`/`env` that override the conf read.

**Rationale:** The autonomous SDLC's "stuck-loop detection" rule is about **iteration-introduced** failures (two identical failures across retries on the same code). This is a single, dev-machine-only, pre-existing flake. The PR description must call this out explicitly so a reviewer knows what to watch for in CI. The five-gate before push will be assessed with this exclusion documented.

**Mitigation:** PR body explicitly calls out the unrelated flake with reproduction steps so the reviewer can spot if CI also fails on the same test (in which case it becomes their problem to triage, not blocked on this branch).
